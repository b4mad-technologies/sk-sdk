# Advisory action cue (rank and explain a visible action)

## Name

`advisory-action-cue` — public presentation metadata that makes one already
visible action easier to notice and understand, without changing what the
world permits.

## Problem

Several actions can be factually visible at once. An author wants to make a
natural next step easier to discover (for example, speaking to a person or
taking a visible exit), but must not turn a UI preference into an eligibility
rule, a hidden target binding, or a dialogue answer contract.

## Forces

- An affordance remains an attempt: the reducer is authoritative about whether
  it succeeds.
- A response to an open dialogue question needs the server-owned occurrence
  contract in [`prompt-occurrence`](./prompt-occurrence.md), not a ranking
  hint.
- A public cue is visible to every client that can already see its action, so
  it cannot carry private state, an entity reference, a payload default, or
  `semantic_context`.
- Different consumers may present the same fact differently. A human shell can
  show the hint; an NPC may use the rank only to break an exact policy tie.

## Solution

Attach `ui.affordance_cue` metadata to an `affordance_template` (by its
exact `template_id`) and declare the namespace **public** — the SDK drops
cue rows whose namespace is not public
(`packages/spellkave-sdk/src/core/readers/affordance_cue.ts:47-53`). The
payload has only optional bounded presentation fields:

```toml
[[metadata_attachments]]
bundle_id = "srd"
namespace = "ui.affordance_cue"
payload_json = '{"rank":4,"hint":"Speak directly to a visible person."}'
source = "manifest"
target_kind = "affordance_template"
target_ref = "srd/speak-to/affordance"   # the template_id, not the action id

[[metadata_namespaces]]
audience = "public"
bundle_id = "srd"
namespace = "ui.affordance_cue"
```

`rank` is an integer from 0 through 9. It breaks an otherwise exact local
presentation or policy tie only. `hint` explains the suggestion in human
language. Consumers ignore malformed or absent fields. The SDK joins the first
available cue from the action's already-authoritative template source and
projects it alongside the action; no reducer argument changes.

An open prompt occurrence always wins over a cue. The client sends
`semantic_context` only when it selected a real prompt response; a cue never
creates it.

## TOML example

Generated by
`packages/spellkave-srd-cc/src/ui/affordance-cues.ts` into
`packages/spellkave-srd-cc/fixtures/ui/affordance-cues.toml`. That generator
currently attaches a speech cue and a movement cue to the SRD playing-the-game
templates:

```toml
# pattern: advisory-action-cue
[[metadata_attachments]]
bundle_id = "srd"
namespace = "ui.affordance_cue"
payload_json = '{"rank":2,"hint":"A visible exit can take you onward."}'
source = "manifest"
target_kind = "affordance_template"
target_ref = "srd/affordance/step"
```

## Proof

- `packages/spellkave-sdk/src/__tests__/readers.test.ts` proves a public
  attachment projects into `readManipulationContext(...).actions[].cue`.
- `apps/play/src/lib/fact-composer.test.ts` proves prompt responses retain
  precedence over ranked ordinary actions.
- The TypeScript explore scorer that proved an NPC uses rank only for an exact
  affordance-score tie was deleted with the TypeScript host (sk-jay0.1.55.60.8).

## Known misuse / anti-pattern

- Putting `target_ref`, an entity id, a speech payload, or `semantic_context`
  in cue metadata. Those are an attempt's data, not a public presentation hint.
- Raising `rank` to make an action eligible, or lowering it to hide one. The
  server and ordinary visibility rules remain authoritative.
- Using a cue for "the answer to this question." Author a prompt occurrence
  instead; only it captures the response set and addressee safely.

## SRD features that use this

The playing-the-game speech and movement templates. Further authored examples
must be public action-level hints with the same bounded payload shape.
