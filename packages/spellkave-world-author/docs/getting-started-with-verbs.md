# Getting started with verbs

AUTHOR **verb deep-dive** — linked from the start-here guide `onramp`
(`sk docs onramp`). This page does **not** replace onramp; it walks the
multi-call AUTHOR verb flow once you already know the three command groups
(AUTHOR / PLAYER / file commands) and that TOML is the underlying model.

Write manifest ROWS by calling the `spellkave_*` AUTHOR tools, not by
hand-editing TOML text. Full parameter reference: `tool-reference`
(`sk docs tool-reference`). Underlying row shapes: `manifest-format`.
Worked examples: `sk docs` → Worked examples.

## Why verbs, not TOML text

Hand-writing manifest TOML means holding the whole row/field schema in your
head, getting `bundle_id`/`depends_on`/id-namespacing right by hand, and only
discovering a mistake when the validator rejects a wall of text with a line
number. Each staging verb instead:

- wraps the SAME `@spellkave/world-author` row-generation machinery a
  hand-authored bundle ultimately produces, so nothing is reinvented and the
  output validates identically;
- validates its own inputs BEFORE writing anything, and an unsupported shape
  fails loudly, **naming the offending parameter** — never a bare TOML line
  number;
- merges into your workspace's scratch manifest with **upsert-by-key**
  semantics (see [Idempotent re-authoring](#idempotent-re-authoring) below),
  so re-running a call to fix a typo replaces the row instead of duplicating
  it.

## The 4-call fireball flow

The worked example this flow reproduces is
[`examples/aoe-damage-spell.md`](./examples/aoe-damage-spell.md) (its
manifest, `examples/aoe-damage-spell.toml`, is generated by
`scripts/doc-examples/aoe-damage-spell.ts`). Four write calls — plus the
existing `spellkave_apply_manifest_delta` to flush the result — produce a
manifest that validates with **zero diagnostics**. Two tests back this:

- `packages/spellkave-tool-authoring/src/__tests__/doc-contract.test.ts`'s
  `DOC-PROMISE: getting-started-with-verbs#the-4-call-fireball-flow` case
  runs the exact snippets below and asserts zero diagnostics, well-formed
  node ids, and that apply passes the finished TOML through unchanged.
- `packages/spellkave-session/src/player-tools/__tests__/authoring-verbs.test.ts`
  ("is semantically equivalent to docs/examples/aoe-damage-spell.toml")
  runs the same four calls with the example's hierarchical node ids
  (`aoe_blast/arena/center`, `aoe_blast/arena/fringe`, place graph
  `aoe_blast/arena`) and compares the spell-cluster and resource rows
  field-by-field against the example (modulo generated ids, comments, and two
  documented column divergences); entity and place rows are compared on
  counts and key fields only.

The step-1 snippet below is simplified to flat node ids (`aoe_blast/center`),
so its place graph is `aoe_blast`, not the example's `aoe_blast/arena`.

1. **`spellkave_author_place`** — author the place graph (one call per
   graph): a list of nodes sharing one common parent path, plus any edges
   between them. Node ids are `<place_graph_id>/<local_id>`. `place_graph_id`
   may itself contain `/` (a hierarchical id like `aoe_blast/arena`);
   `local_id` is the **last** path segment and must not contain `/`.
   Doctor check `node_id_well_formed` splits on the last slash.

   ```jsonc
   {
     "bundle": "aoe_blast",
     "nodes": [
       { "id": "aoe_blast/center", "name": "Arena Center" },
       { "id": "aoe_blast/fringe", "name": "Arena Fringe" }
     ],
     "edges": []
   }
   ```

2. **`spellkave_define_resource`** — author the resource pool the spell will
   drain (a `resource_definitions` row + tag satellites). Write verbs never
   fabricate bounds for a pool they didn't create, so if `spellkave_define_behavior`'s
   `effect.write.resource` needs a pool that doesn't exist yet, define it
   first.

   ```jsonc
   {
     "bundle": "aoe_blast",
     "id": "hp",
     "display_name": "Hit Points",
     "min_value": 0,
     "max_value": 30,
     "recovery_rule": "long_rest",
     "initial_value": 30
   }
   ```

3. **`spellkave_place_actor`** — declaratively place actor instances. The
   `placements` array shape places the SAME actor kind split across
   MULTIPLE place nodes in ONE call (mutually exclusive with the flat
   `at`/`count`/`resources` shape) — here, 3 npcs at the blast center (the
   caster plus two targets) and 1 at the fringe (a bystander that must stay
   outside a radius-0 blast, proving the selector is genuinely bounded).

   ```jsonc
   {
     "bundle": "aoe_blast",
     "kind": "npc",
     "placements": [
       { "at": "aoe_blast/center", "count": 3 },
       { "at": "aoe_blast/fringe", "count": 1 }
     ]
   }
   ```

4. **`spellkave_define_behavior`** — author the spell itself: a capability +
   action + outcome + consequence chain, driven by the SAME `clusterRows`
   builder the SRD content drivers use. `grant_to` binds the capability to
   the caster (the first placed actor key); `effect.write.resource` must
   already resolve (step 2 authored it) — no verb auto-creates a pool it
   didn't itself define.

   ```jsonc
   {
     "bundle": "aoe_blast",
     "id": "firebloom",
     "grant_to": "aoe_blast/npc_1",
     "offered_when": { "reach": "same_node" },
     "action_class": "spell",
     "effect": {
       "primitive": "ForEachActorInRadius",
       "shape": { "id": "core/area/node_ball", "radius": 0 },
       "per_target_gate": "d20 < 13",
       "write": { "primitive": "ModifyResource", "resource": "aoe_blast/hp", "delta": "-d6" }
     }
   }
   ```

5. **`spellkave_apply_manifest_delta`** — **commit** the finished workspace
   scratch to the active connection-level [target](#the-target-model-stage-then-commit).
   Call with **no arguments** (do not paste TOML): the tool reads the scratch
   pad. `live` dispatches through `r_apply_manifest_delta` (upsert semantics,
   ADR-0085); `local` merges into a target folder's own `manifest.toml`.
   Optional `toml` is only an escape hatch for an external delta.
   On `live`, the tool **waits for a push**: a new digest seal (ok) or a
   `manifest_apply_outcome` row (the MF-APPLY code). Enqueue is not success.
   A mid-segment commit error rolls that firing's writes back; enqueue has
   already armed a delayed `MF-APPLY-029` quarantine, so the waiter still
   sees a named outcome about 90 s later (`MANIFEST_APPLY_QUARANTINE_SLACK_SECS`,
   the world API) instead of waiting for the SDK's
   15-minute watchdog (`MANIFEST_APPLY_WATCHDOG_MS`,
   `packages/spellkave-sdk/src/manifest-apply.ts`).

None of the four write calls needed a `spellkave_write_manifest_toml`-style
pre-seed: every write verb self-scaffolds its own `[[bundles]]` header the
first time it sees a new `bundle` — a genuinely EMPTY workspace is a valid
starting point.

## Smart defaults

Every write verb accepts an OPTIONAL `bundle` parameter. When you omit it,
the verb falls back to `context.defaultBundle` — the workspace/connection-level
default a host can wire once per authoring session instead of repeating
`bundle: "<id>"` on every call. Per-call `bundle` always wins when both are
set; a host juggling multiple bundles in one session simply keeps passing
`bundle` explicitly and the default is never consulted.

Other defaults worth knowing before you pass a value you don't need to:

- `spellkave_author_place`'s node `name` defaults to a title-cased local id
  when omitted.
- `spellkave_query`'s `target` parameter, when omitted, reads the UNION of
  the workspace scratch manifest plus whatever connection-level target or
  live db is configured — `result.source` always says which sources were
  actually consulted (`"workspace"`, `"workspace+local"`, or
  `"workspace+live"`).
- `spellkave_query`'s detail shape (`kind` + `id`) defaults `refs` to
  `"both"` — the row plus its outbound AND inbound refs — since a bounded
  single-row detail call is exactly where the ref payload earns its keep;
  list/summary shapes never carry refs (see
  [The target model](#the-target-model-stage-then-commit) below).

See [`tool-reference.md`](./tool-reference.md) for the full, generated
default/required table per parameter, per verb.

## Authored observation prose (#1968 B-9)

`spellkave_define_behavior`'s outcome body accepts an optional `observation`
string — authored prose describing what a PLAYER perceives on a successful
manipulate or sensing outcome (the `outcome_templates.description` column
under the hood; #1921/#1923's `receipt`/`observation` split in the companion
agent's act tools). Omit it and nothing changes: the tool result carries its
existing honest `observation: null` + `observation_gap` shape, exactly as it
did before this field existed.

Two things worth knowing before you author one:

- **It is a bounded, closed vocabulary, not free text with variables.** The
  ONLY placeholders you may use are `{target_name}`, `{actor_name}`, and
  `{place_name}` — resolved from data the player is already authorized to
  see, never a raw id. A placeholder outside that set (or anything that
  dereferences live state — HP, a resource value, a condition) is rejected at
  validation time; state-dependent narrative belongs in the DSL outcome
  expression, not here. General-purpose prose interpolation is intentionally
  NOT supported — this is a single authored line, not a template language.
- **It is NOT a discovery-gated reveal channel.** `observation` text is
  world-public static prose, exactly like a place node's `description` — it
  reads identically for every player who successfully triggers that outcome.
  The epistemic gate that decides WHETHER a player sees anything at all
  happens earlier, in the (owner-gated) provenance correlation that resolves
  which outcome fired — never in this text. If you want a conditional reveal
  (a hidden trap, a disguised NPC, "you now know the guard is lying"), that
  is a DIFFERENT, already-owned mechanism (the discovery-validated sensing
  path, ADR-0081 G-2) — do not try to smuggle a reveal into authored prose by
  writing two outcome templates and hoping only one is ever selected.

## Idempotent re-authoring

The folding verbs (`spellkave_define_resource`, `spellkave_define_entity_type`,
`spellkave_define_roll_table`, `spellkave_define_condition`,
`spellkave_define_niche`, `spellkave_define_capability`, and
`spellkave_define_behavior`) merge by **upsert-by-key**: re-authoring the
SAME `bundle` + `id` REPLACES the row and every satellite wholesale — a
second call with fewer tags, say, drops the stale ones rather than leaving
them behind. This is what makes "call the verb again to fix a mistake"
safe: you never need to hand-delete a stale satellite row first.

`spellkave_write_rows` — the generic escape hatch for any row kind the
narrower verbs don't cover — upserts when the target `kind` has either a
single-column natural key (`commit.rs`'s ADR-0085 upsert discipline) or a
wider ordered composite key (ADR-0146: junction/satellite rows such as
`*_tag`, `entity_definition_initial_*`, `actor_capabilities`, `object_state`,
and more). A row whose full key already matches an existing row REPLACES it;
a row that omits any key field can only append, never collide. The one kind
with no key of either shape is `consequence_frame_writes` (its identity is the
whole ordered list per `template_id`, not a per-row key) — it stays
APPEND-ONLY through this verb; author it via its own consequence-authoring
verb instead. For a wholesale reseed of a whole satellite set (not just
avoiding a duplicate), the parent folding verb is still the better tool.

`spellkave_set_metadata` is the normal generic path for metadata, not a
`spellkave_write_rows` shortcut. A root call replaces only its named
`[metadata]` keys. An attachment call upserts by its live identity
`(target_kind, target_ref, namespace, bundle_id)` and replaces its payload and
source; a batch either persists together or leaves the scratch unchanged.
Namespace registrations use their owner identity and reject a foreign owner.
See [`metadata-attachments.md`](./metadata-attachments.md) for the three
target shapes.

## `spellkave_write_rows` and spatial niche attachments

`spellkave_define_behavior` auto-generates a `spatial_niche_attachments` row
binding its `capability:<cap>` niche to `grant_to`'s own node. It resolves
placement from the workspace first, then the active target, and requires a
nonblank `place_node_id`. A live AUTHOR may know the actor without being
allowed to read its node; in that case the verb immediately names `grant_to`
and `place_node_id` in an error and leaves scratch unchanged. Supply the
actor's known current placement as an `actor_spatial_locations` workspace
row before retrying; do not guess a node. The regression is covered by
`packages/spellkave-session/src/live/caster-placement.live.test.ts`.
`spellkave_write_rows` does **not** generate attachments for you: it is the
generic escape hatch for any row kind, with no `grant_to`/caster-node concept of its own to
auto-attach against. An `action_definitions` or `affordance_templates` row
authored via `spellkave_write_rows` whose niche is **place-provided** (the
default: `niche_definitions.provider` empty or `"place"`, and the fail-closed
fallback for a niche with no definition row) and has no matching
`spatial_niche_attachments` row anywhere in the workspace or your active
target will never be selected by `r_manipulate`. The rejection names the
cause: its hint carries `niche_unresolved` (no niche resolved for the
actor's node), not the `predicate_rejected` marker an ordinary attack-roll
miss carries (the world API;
tests in `selection/candidates/tests/turn_aware.rs`). Read the failure kind
before assuming a bad roll. **Do not leave a `capability:*` niche without a `provider`.** That is how a
carrier-bound class feature silently becomes room-scoped (sk-0m4.69).
Author `provider = "actor"` for verbs that travel with the hero; author
`provider = "place"` only when you mean a node. Ordinary niches still default
to place-provided when `provider` is empty — that default is not flipped.
Pre-flight **`WA-CAP-002`** is fatal when a `capability:*` niche has no
definition row or an empty provider. The tool call also surfaces a
non-blocking `WARNING` when an authored niche has no attachment. Today that
warning fires for every such niche, including `provider = "actor"` niches
that need no attachment (`missingNicheAttachmentWarnings` in
`packages/spellkave-tool-authoring/src/authoring-verbs.ts` never reads
`provider`; bug `sk-jay0.7.173.2`), so for an actor-provided niche it is
noise. Otherwise treat either as a to-do — author the missing
`niche_definitions` (and, for place-provided niches, the
`spatial_niche_attachments`) row before relying on the action/affordance.

## The target model: stage, then commit

Every write verb writes into the WORKSPACE — an in-memory (or host-persisted)
scratch manifest, never applied anywhere until you say so. This is the
staging step. `spellkave_query` lets you inspect staged rows before committing;
dispatch is inferred from which fields you pass,
no `mode` flag:

- **Omit `kind`** for a summary: bundle ids + a row-kind → count map (what
  `spellkave_manifest_inspect` used to answer alone) — generalized across
  `target`, and optionally scoped to one `bundle`.
- **Pass `kind`** (optionally with `pattern`, a substring filter) for a
  bounded, ids-only catalog list for that row kind — what `spellkave_lookup`
  used to answer, generalized from 4 hardcoded kinds to ANY
  `ROW_KIND_NATURAL_KEY` name (`capability_definitions`,
  `affordance_templates`, `action_definitions`, `outcome_templates`,
  `entity_definitions`, … the same vocabulary `spellkave_write_rows` and
  every `spellkave_define_*` verb already use).
- **Pass `kind` + `id`** for the complete authored row, its source, and (by
  default) its refs — the definition-lookup gap this merge closes. Every
  kind a `define_*` verb (or `spellkave_write_rows`) can WRITE is now also
  readable in full by the SAME name, not just the 4 catalog kinds
  `spellkave_lookup` used to expose. `outbound_refs` lists fields on the row
  pointing elsewhere; `inbound_refs` lists every OTHER row anywhere in the
  resolved source whose own field points AT this row, grouped by
  referencing kind — chase a chain (e.g. a capability → its
  `affordance_templates` → their `action_definitions` → `outcome_templates`)
  by re-calling `spellkave_query` with a ref's own `{kind, id}`; no separate
  traversal tool needed.

Looking up existing ids — in the workspace, and optionally in a
connection-level `target` or live db — BEFORE you author against them beats
write-then-fail-on-a-dangling-ref; checking the referenced IDs with `spellkave_query` catches missing
references before the write. Live state can change before commit, so this
inspection does not replace server admission.

`spellkave_apply_manifest_delta` is the commit step of the authoring loop:
write verbs stage into the workspace scratch; apply sends that
scratch to whichever **connection-level target** is active —

- **Default call `{}`** — reads `workspace.readToml()` and flushes it (`source:
  "scratch"`). No TOML paste, no path/id pointer needed beyond "commit what I
  just authored".
- **Optional `toml`** — escape hatch for an external/ad-hoc delta string
  (`source: "toml"`), not the normal path after verbs.
- `live` — dispatches through the `r_apply_manifest_delta` reducer (upsert
  semantics, validated server-side against live world ∪ delta, ADR-0085).
  Living roll tables are in that union (sk-3h5): a delta that never mentions
  a table still sees its published headers, entries, and die tags, so
  `MF-VAL-317` / `roll_table()` refs cannot skip the world that is already there;
- `local` — renders/merges the batch into a target folder's own
  `manifest.toml` on disk. It validates that root together with its
  includes and `depends_on` closure, as `sk validate --bundle --dep` does.
  When the call creates a new root with one bundle, it also writes
  `applyset = "<bundle_id>"`, which `sk dev seed` requires, and reports
  it as `applyset` in the result. An existing root keeps its own line.
  A write verb's scaffolded `[[bundles]]` header never replaces a bundle
  row the root already has; call `spellkave_define_bundle` to change it.

Calling `spellkave_apply_manifest_delta` with neither a `target` nor the
legacy `context.applyDelta` port wired throws, naming both — offline
authoring with no configured destination has nothing to flush to. An empty
scratch with no `toml` also throws (nothing to commit). Workspace authoring
verbs (`author_place`, `place_entity`, `place_actor`, `define_resource`,
`define_behavior`) and offline inspect/query work without a connection.
Running-world get/describe/diff and live writes require their current connected
reader or apply port.

`spellkave_apply_manifest_delta` commits a scratch delta. Editing the FILES
of a root that is already on a world (a seeded root with an `applyset` line)
is a different loop: `spellkave_applyset_diff` / `sk diff -k <dir>` shows
what changed against the world's applyset memory, and
`spellkave_applyset_apply` / `sk apply -k <dir>` sends only those rows — no
hand-built delta, no wipe and reseed (ADR-0145; rules and limits in the `sk`
README, "Applyset diff and apply").

To remove a placed entity from local author files, use
`sk --target <root> --workspace <scratch.toml> remove_entity --entity-key <exact-key>`.
Unlike staging verbs, this immediately removes the root-owned entity and its
owned instance rows from both files. Other scratch rows remain staged. Include
ownership and surviving references refuse with a repair hint. It sends nothing
to the world; run `sk apply -k <root> --prune --dry-run` to inspect the prune,
then apply it explicitly. See the CLI README's "Remove a placed entity from
author files" for the local-file and failure contract.

This comparison loop currently requires exact-publisher baseline access in CLI,
HTTP MCP and local stdio MCP. A non-publisher receives `baseline_unavailable`
before baseline subscription or enqueue, including a fresh root or `--force`.
Regional baseline delivery is tracked in sk-jay0.3.24.160; see
[reading a running world](./reading-a-world.md). Direct binding-only deltas and
scoped instance reads retain their separate admission lanes.

The diff also compares readable live values. A seeded row with no applyset
memory is `adopt`: equal values establish memory without rewriting the row;
a difference is a conflict. Changed file rows compare against the comparable
hash recorded at the previous sealed apply. Unchanged files may show drift
for inspection without scheduling a write. `sk apply -k <dir>` refuses
conflicts before sending; `--force` requests that the file values win and
also retains takeover and publisher entity-prune overrides. Scoped entity
prune still requires publisher closure. The result's
`force_used` array names each override actually used.

The human report distinguishes world-added rows taken with a pruned entity,
rows left behind, and authored rows changed in the world since the last
apply. `not_checked` explains missing comparisons rather than claiming
agreement: unavailable or incomplete caller coverage, unsupported kinds, unread
live placement, or older memory without comparable hashes. Current role-scoped
projections supply comparison for the eight supported instance kinds described
in [reading a world](reading-a-world.md). Apply refuses unchecked scoped writes;
`--force` cannot manufacture missing coverage.
Server ownership and extent checks still apply to adoption and forced writes.
The seeded-adoption/refusal assertions live in
`crates/spellkave-authoring/src/diff_apply.rs` and
`packages/spellkave-tool-authoring/src/__tests__/applyset-tools.test.ts`.
The [captured AUTH-37 local journey](../../../sandbox/diff-drift-decision/README.md)
also proves the actual CLI refusal, explicit recovery and independent world
postconditions. It runs the workspace-installed CLI in an external temporary
directory. [The scoped reader evidence](../../../sandbox/role-scoped-world-read/README.md)
also covers the bound author's source and unchecked-force refusal; hosted
delivery and portable publication remain the `.45`/`.56` follow-up surfaces.

## Authority reconciliation during live apply

Live apply is segmented; it is not a transaction over every manifest row.
Role definitions, aggregations, bindings and all affected realised grants are
reconciled together in atomic authority segment B, after the earlier structural
segment A. Changes cannot leave a partially updated authority set.

At enqueue the server records the original applying identity and the IDs of
bindings admitted for realisation. It rechecks live authority before the drain
writes: expiry, revocation, current role composition and old/new extent coverage
can refuse work that was previously admitted. `$sender` resolves using the
original submitter. The queued sender/verdict fields are server-owned and are
not manifest fields, authoring hints or export data.

The authority unit is bounded to **4096 authority-table row writes**, including
identity mirrors and realised grants. This is not a bound on the factual-context
materialisation pipeline, which keeps its existing drain. An oversized authority
unit is rejected before enqueue rather than divided into partial authority
commits (the world API).

If segment B fails, prior segment A writes can remain. Preserve the submission's
quarantine and unknown-base state; do not report successful reconciliation or
clear recovery state because the authority unit rolled back. Inspect live state,
correct the cause and reconcile/resubmit through the existing applyset recovery
flow. Module migration defaults an old queue's sender to `Identity::ZERO` and
its optional realised-binding verdict to `None`; queued authority work without
a valid recorded verdict fails closed before authority writes and needs
resubmission. Authors must not manufacture those hints.

Persistent rollout uses two publishes: first publish this schema-compatible
module with the binding table and defaulted queue/runtime fields while the
publisher/genesis grant lane remains open. Apply migrated bundles as publisher
on every catalog world, realising bindings and withdrawing the old reserved
grants. Follow-up .67 supplies the second publish to close the bare-grant lane.
Preserve existing authority and queued-state evidence during migration; this
guide does not claim hosted rollout has been exercised.

## Extent-scoped apply

A presence-held apply grant authorizes rows inside its live extent. A Bundle
grant covers definitions and owned root graphs through applyset memory; a
PlaceGraph or Party grant covers placed edits. The server checks pre-image and
post-image placement and separately checks targets such as an entity receiving
a capability or state write. A new destination cannot authorize an old foreign
pre-image. The original sender and its admitting bindings are rechecked before
every mutation segment; a grant created by the same request cannot authorize a
later segment.

`sk diff -k <dir>` uses the shared Rust advisory to show ownership refusals
before sending; placement remains "server decides" because it needs private
live facts. `sk apply -k <dir>` uses the additive scoped applyset reducer.
Raw delta consumers retain their existing signatures. The scoped and
presence-held paths are active; deployed ordinary-body delta/bundle adapters
remain transitional until `.67` and universal activation `.84`.

| Code | Reason |
|---|---|
| `MF-APPLY-037` | Part entry bundle disagrees with its row or root bundle list |
| `MF-APPLY-041` | Placement, target or placeless row lies outside held extents |
| `MF-APPLY-042` | Ownership takeover or root bundle claim exceeds held Bundle extents |
| `MF-APPLY-043` | Authored row exists but no applyset lists it |
| `MF-APPLY-044` | Non-publisher whole-world replacement |

For an initial-state `object_state` row that no applyset lists, a raw
owner-preserving overwrite can follow the entity's target reach while keeping
the live stamp. It still needs placement admission. Claiming memory, changing
the stamp or retracting that satellite additionally requires all target owners
inside the writer's Bundle extents, with at least one owner (`042`). Listed
state rows retain ordinary ownership checks. Do not restamp runtime state to
make a scoped request pass; `.91` supplies ownership at its actual cause.

Aldwin has a publisher-authored Bundle binding over `elven_mini`. Its regional
binding admits placed edits and its Bundle binding admits own-adventure
prompt definitions. The interim prompt consumer claims one explicit adventure
bundle per prompt root, supports identical retry and retirement, and refuses
prompt IDs outside `<adventure>/prompt/runtime/`; `.92` owns its runtime-state
replacement. Shared `dm` and foreign-adventure definition edits remain refused.

The applier and publisher can read `applied_by` and `applied_via` through
`visible_manifest_apply_provenance` and existing manifest/applyset readers.
Unrelated callers see commit metadata without principal fields. Denied enqueue
writes no memory; later refusals preserve earlier admitted commits and the
existing quarantine/unknown-base recovery. The live admission and independent
observer controls are in `extent-scoped-apply.live.test.ts`; the scope and
satellite unit controls are in the world API.

## Live authoring: role grants and character binding

A second live apply needs continuing manifest admission after genesis. An
admitted grantor creates a [role binding](./roles.md#bind-a-role-to-a-subject)
through [grant_role](./grants.md), giving the author the role and explicit
extent needed by its later operations. Role vocabulary alone and inert bindings
supply no live authority. `spellkave_bind_actor` directs `frontier.*` requests to
`spellkave_grant_role`; it writes character identity and ordinary gameplay grants:

```jsonc
{
  "bundle": "us_dungeon",
  "entity_key": "us_dungeon/npc_1",
  "capabilities": [{ "capability_id": "core/walk", "source": "core" }]
}
```

`identity` defaults to `$sender`, resolved to the original applying connection.
`capabilities` defaults to `[]`: omit it for identity-only binding. A privileged
role grant realizes a separate presence body; it does not attach authority to
this playable character. The low-level publisher/genesis bare-grant adapter
remains transitional until `.67`; the character tool uses role grants for
privileged requests.

A manifest-written identity binding has `connection_id: None` and survives
disconnects. Ordinary character binding upserts remain distinct from role-bound
NPC membership: changing the latter requires covering D6 bind rights, even for
an existing transient claimant with separate apply authority. Before starting
a role-bound NPC host, the publisher/operator applies its retained identity as
a durable primary binding. The host claims that existing binding, which keeps
it durable. An already durable self-bind can be a no-op; a connection-scoped
claim cannot bootstrap presence authority by applying its own `$sender` delta.
See [NPC bootstrap](./dm-oversight.md#the-default-the-publisher-bootstraps-the-npc-host).

`spellkave_bind_actor` requires an existing `actor_spatial_locations` row; place
the character first with `spellkave_place_actor`. Role presence bodies are
created by binding reconciliation and are not placed or claimed through this
character tool. The same optional `capabilities` array remains useful for
ordinary gameplay grants such as `core/walk`; see
[movement gates](./running-an-authored-act.md#movement-gates-capability-reach-are-independent)
for the separate capability and movement-resource checks.

## When a verb refuses

Every write verb validates its own inputs and, separately, re-validates the
WHOLE merged workspace manifest before persisting anything — a call whose
merged manifest carries a **blocking** diagnostic is rejected and nothing NEW
is written. Which diagnostics block depends on the verb
(`commitOrReport`'s `blockOn` in
`packages/spellkave-tool-authoring/src/authoring-verbs.ts`):
`spellkave_write_rows`, `spellkave_set_metadata`, `spellkave_define_bundle`,
`spellkave_define_trace_kind`, and the catalog `spellkave_define_*` verbs
(entity type, roll table, condition, niche, affordance, capability,
consequence, action, session, action verb) block on `fatal` only; the
remaining write verbs (place, actor, entity, resource, behavior, …) block on
any diagnostic. With a connection-level `context.target` wired, every verb
blocks on `fatal` only. Non-blocking warnings are returned but do not stop
the write.
Three distinct failure shapes, in the order a call actually hits them:

- **A parameter-shape violation** (e.g. a placement tool called with both
  `at` and `placements` set, or neither) is rejected before any row is even
  generated, and the call **throws**, naming the offending parameter(s)
  directly.
- **A missing structurally-required field** on a `spellkave_write_rows` row
  (e.g. an `entity_definitions` row with no `display_name`) also **throws**
  — this fails at the row-rendering step, before the validator ever runs,
  because the field is required by the row's own Rust schema shape, not
  merely checked by a validator pass. The thrown message names the missing
  field, but it is a schema/parse-level error, not an `MF-VAL-nnn`
  diagnostic — the narrower `spellkave_define_*`/`spellkave_place_*`/
  `spellkave_author_place` verbs never hit this shape at all, since they
  only ever expose parameters for fields their own TypeBox schema already
  makes required.
- **A blocking validator diagnostic** proper (e.g. a dangling reference like a
  `capability_id` that resolves to no authored row) surfaces the validator's
  own diagnostic — including its `MF-VAL-nnn` code — **gracefully, in the
  tool result** (`details.ok === false`, never a thrown error), mapped back
  to the offending row/param (`details.diagnostics[].param`), never a bare
  TOML line number in a document you never wrote by hand.

If you hit an intent no documented row kind or DSL form can express, call
`spellkave_declare_inexpressible` — a well-justified "I cannot express
this" is a successful finding, not a failure. If the packaged docs
themselves led you to expect different validator behavior than what you
observed, call `spellkave_note_doc_gap` — it does not end your run, and it
is exactly how promises like the ones this doc makes get corrected.
